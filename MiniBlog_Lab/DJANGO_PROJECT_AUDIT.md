# 1. Project Overview

MiniBlog_Lab - учебный Django-проект для последовательного изучения базовых механизмов Django: project/app structure, URLConf, views, templates, models, migrations, ORM, admin, forms, class-based generic views, authentication/authorization и relationships.

Фактическая версия Django: `6.0.7`. Это видно из `config/settings.py`, комментариев в миграциях и подтверждено командой `python3 -m django --version`.

Приложения проекта:

- `core` - статические/учебные страницы и demo-form.
- `posts` - блоговые публикации, категории, CRUD через CBV, авторизация действий.
- встроенные Django apps: `admin`, `auth`, `contenttypes`, `sessions`, `messages`, `staticfiles`.

База данных:

- SQLite.
- Файл: `BASE_DIR / "db.sqlite3"`.
- Настройка: `django.db.backends.sqlite3`.

Основные сущности:

- `Post` - публикация блога.
- `Category` - категория публикации.
- `User` - стандартная пользовательская модель Django, используется через `settings.AUTH_USER_MODEL`.

Текущая архитектура:

- project package: `config`;
- app URLConfs: `core/urls.py`, `posts/urls.py`;
- корневой URLConf подключает `core` на `/`, `posts` на `/posts/`, auth login/logout на `/login/` и `/logout/`;
- templates ищутся через `APP_DIRS=True`, глобальной директории templates нет;
- статический CSS лежит в `core/static/css/main.css`;
- CRUD постов реализован через generic CBV: `ListView`, `DetailView`, `CreateView`, `UpdateView`, `DeleteView`;
- создание/редактирование/удаление постов защищено login/ownership-проверками.

## Post -> User relationship

Фактическая реализация:

```python
author = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    on_delete=models.CASCADE,
    related_name="posts",
)
```

Смысл:

- каждый `Post` имеет одного обязательного автора;
- один `User` может иметь много постов;
- при удалении пользователя его посты удалятся (`CASCADE`);
- обратная связь: `user.posts.all()`;
- концептуальный foreign key: `posts_post.author_id -> auth_user.id`.

Важно:

- используется `settings.AUTH_USER_MODEL`, а не прямой импорт `User`, это хороший текущий паттерн;
- поле обязательное: `null=False`, `blank=False` по умолчанию;
- в `PostCreateView.form_valid()` автор назначается автоматически из `request.user`.

## Post -> Category relationship

Фактическая реализация:

```python
category = models.ForeignKey(
    Category,
    on_delete=models.SET_NULL,
    related_name="posts",
    null=True,
    blank=True,
)
```

Смысл:

- пост может иметь одну категорию или не иметь категории;
- одна категория может иметь много постов;
- при удалении категории посты сохраняются, а `category_id` становится `NULL`;
- обратная связь: `category.posts.all()`;
- концептуальный foreign key: `posts_post.category_id -> posts_category.id`.

Важно:

- `null=True` разрешает `NULL` в базе;
- `blank=True` разрешает пустое значение в формах;
- категория пока не включена в `PostForm`, поэтому через форму создания/редактирования поста пользователь ее выбрать не может.

# 4. Views / CBV

Файл: `posts/views.py`.

| View | Base class | Mixins | Purpose | Template | Success URL | Important overrides |
|---|---|---|---|---|---|---|
| `PostListView` | `ListView` | none | Список опубликованных постов | `posts/post_list.html` | none | `get_queryset()`, `get_context_data()` |
| `PostDetailView` | `DetailView` | none | Детальная страница опубликованного поста | `posts/post_detail.html` | none | `get_queryset()` |
| `PostCreateView` | `CreateView` | `LoginRequiredMixin` | Создание поста авторизованным пользователем | `posts/post_form.html` | `reverse_lazy("posts:post_list")` | `form_valid()` assigns `form.instance.author` |
| `PostUpdateView` | `UpdateView` | `LoginRequiredMixin`, `UserPassesTestMixin` | Редактирование поста владельцем | default `posts/post_form.html` | `reverse("posts:post_detail", pk=self.object.pk)` | `test_func()`, `get_success_url()` |
| `PostDeleteView` | `DeleteView` | `LoginRequiredMixin`, `UserPassesTestMixin` | Удаление поста владельцем | default `posts/post_confirm_delete.html` | `reverse_lazy("posts:post_list")` | `test_func()` |
| Login | `LoginView` | n/a | Вход пользователя | `registration/login.html` | controlled by `LOGIN_REDIRECT_URL` | configured in `config/urls.py` |
| Logout | `LogoutView` | n/a | Выход пользователя | default/no custom template needed for POST logout | controlled by `LOGOUT_REDIRECT_URL` | configured in `config/urls.py` |

## PostListView

Фактически:

```python
def get_queryset(self):
    return Post.objects.filter(
        is_published=True
    ).order_by('-created_at')
```

Особенности:

- показывает только опубликованные посты;
- сортирует новые посты сверху;
- задает `context_object_name = "posts"`;
- добавляет `context["page_title"] = "Все публикации"`.

Подозрительность:

- шаблон выводит `{{ posts_count }}`, но view не передает `posts_count`. Значение будет пустым.
- query не использует `select_related("author", "category")`, хотя шаблон обращается к `post.author` для permission checks. Это может создавать N+1 по `author` при списке.

## PostDetailView

Фактически:

```python
def get_queryset(self):
    return Post.objects.filter(is_published=True)
```

Особенности:

- неопубликованные посты недоступны даже владельцу через detail URL;
- нет `get_context_data()`, хотя шаблон ожидает `{{ page_title }}` и `{{ post_id }}`. Эти значения будут пустыми.

## PostCreateView

Фактически:

- требует login;
- использует `PostForm`;
- `success_url = reverse_lazy("posts:post_list")`;
- в `form_valid()` делает `form.instance.author = self.request.user`.

Здесь нет `commit=False`, потому что generic `CreateView` сохраняет `form.instance` после `form_valid()`. Для текущей задачи автор назначается корректно.

## PostUpdateView

Фактически:

- требует login;
- разрешает редактирование только автору;
- использует `PostForm`;
- после успешного обновления ведет на detail текущего поста.

Подозрительность:

- `get_queryset()` не ограничен `is_published=True`, значит владелец может открыть update для draft-поста. Это может быть нормально.
- после сохранения draft-поста redirect идет на `PostDetailView`, где `get_queryset()` показывает только `is_published=True`. Если владелец сохранит `is_published=False`, redirect на detail может дать 404.

## PostDeleteView

Фактически:

- требует login;
- разрешает удаление только автору;
- после удаления ведет на список постов.

Подозрительность:

- как и update, delete доступен для draft-постов владельца, если известен URL. Это может быть желательным.

# 5. Authentication & Authorization

Фактическая реализация:

## LoginRequiredMixin

Используется в:

- `PostCreateView`;
- `PostUpdateView`;
- `PostDeleteView`.

Эффект:

- неавторизованный пользователь не может создать, редактировать или удалить пост;
- redirect идет на URL name из `LOGIN_URL`.

## UserPassesTestMixin

Используется в:

- `PostUpdateView`;
- `PostDeleteView`.

Ownership-проверка:

```python
def test_func(self):
    post = self.get_object()
    return post.author == self.request.user
```

Эффект:

- только автор поста может редактировать/удалять свой пост;
- чужой пост для update/delete запрещен.

## request.user

Используется в:

- `PostCreateView.form_valid()` для назначения автора;
- templates через `user.is_authenticated` и `user == post.author`.

Author assignment:

```python
def form_valid(self, form):
    form.instance.author = self.request.user
    return super().form_valid(form)
```

## Login/logout URLs

В `config/urls.py`:

```python
path("login/", LoginView.as_view(template_name="registration/login.html"), name="login")
path("logout/", LogoutView.as_view(), name="logout")
```

Settings:

```python
LOGIN_URL = "login"
LOGIN_REDIRECT_URL = "posts:post_list"
LOGOUT_REDIRECT_URL = "posts:post_list"
```

## Template-level permission checks

В `core/templates/core/base.html`:

- если `user.is_authenticated`, показывается username и POST-form logout;
- иначе показывается ссылка Login.

В `posts/post_list.html`:

- Create post показывается только authenticated user;
- Edit/Delete показываются только если `user == post.author`.

В `posts/post_detail.html`:

- Edit/Delete показываются только если `user == post.author`.

Важно:

- template checks улучшают UI, но реальная защита реализована во views через mixins;
- logout сделан POST-формой с csrf token, что соответствует современному поведению Django `LogoutView`.

# 6. Forms

## posts.forms.PostForm

Файл: `posts/forms.py`.

Тип:

- `forms.ModelForm`.

Model:

- `Post`.

Fields:

```python
fields = [
    "title",
    "content",
    "is_published",
]
```

Custom validation:

- нет `clean_<field>()`;
- нет `clean()`.

Где используется:

- `PostCreateView.form_class`;
- `PostUpdateView.form_class`.

`form_valid()`:

- используется в `PostCreateView` для `form.instance.author = self.request.user`.

`commit=False`:

- не используется.

`instance`:

- явно не используется в коде;
- для `UpdateView` instance подставляет сам generic view.

Важное расхождение:

- модель `Post` содержит `category`, но `PostForm` не содержит `category`;
- значит через сайт нельзя выбрать/изменить категорию поста;
- это особенно важно после Stage 11 Relationships.

## core.forms.DemoRequestForm

Файл: `core/forms.py`.

Тип:

Fields:

- `student` - `CharField`, max_length=100, custom widget attrs;
- `email` - `EmailField`;

# 10. ORM / Relationships currently supported

На основании фактических моделей доступны следующие ORM-направления.

## Post -> User

Direct:

```python
post.author
post.author.username
```

Reverse:

```python
user.posts.all()
user.posts.filter(is_published=True)
user.posts.count()
```

Lookups:

```python
Post.objects.filter(author__username="dima")
Post.objects.filter(author__is_staff=True)
Post.objects.filter(author__email__icontains="@")
```

## Post -> Category

Direct:

```python
post.category
post.category.title
```

Reverse:

```python
category.posts.all()
category.posts.filter(is_published=True)
category.posts.count()
```

Lookups:

```python
Post.objects.filter(category__title="Django")
Post.objects.filter(category__title__icontains="python")
Post.objects.filter(category__isnull=True)
```

Note: в пользовательском тексте упоминался пример `category__name`, но фактическое поле модели называется `title`, поэтому реальный lookup - `category__title`.

## select_related()

Подходит для FK/O2O relationships:

```python
Post.objects.select_related("author")
Post.objects.select_related("category")
Post.objects.select_related("author", "category")
```

Особенно уместно:

- `PostListView.get_queryset()`, потому что template сравнивает `user == post.author`;
- `PostDetailView.get_queryset()`, если detail template начнет показывать `author` и `category`.

Фактически в текущих views:

- `select_related()` не используется.

## prefetch_related()

Подходит для reverse FK / M2M:

```python
User.objects.prefetch_related("posts")
Category.objects.prefetch_related("posts")
```

Фактически в текущих views:

- `prefetch_related()` не используется.

Сейчас reverse relationships существуют на уровне модели, но не раскрыты в UI и не оптимизированы во views.
